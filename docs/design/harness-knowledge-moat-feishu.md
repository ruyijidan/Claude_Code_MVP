# 当 Harness 成为标配，知识沉淀才是护城河 / When Harness Becomes Table Stakes, Knowledge Becomes The Moat

**副标题 / Subtitle**

从 AI Team 的工程实践出发，重新理解工作流、知识库与长期复利资产的关系

## 适用版本 / Suggested Use

这是一篇独立的观点与实践总结文。

适合场景：

- 在 Harness 学习专题之外，补充更偏实践与方法论的观察
- 作为团队知识工程方向的对外分享
- 作为资源库中的进阶阅读材料

---

## 文章摘要 / Article Summary

当 Harness Engineering 成为 2026 年最热门的 AI 工程话题，业界争论焦点往往集中在：

- 该用多大的模型
- 该搭多复杂的工作流
- 多 Agent 协同要不要做得更重

但在我们的落地实践里，真正越来越清晰的一个事实是：

**构建 Harness 工作流不是最终目的，私域和团队知识的沉淀，才是真正的技术护城河。**

模型会迭代，工具链会更新，工作流会重构。  
但你的团队在特定业务领域积累的领域模型、架构决策、最佳实践、已知陷阱、业务流程和验证经验，这些知识不会因为模型换代而失效。

这篇文章想回答五个问题：

1. 为什么我们认为知识沉淀比工作流本身更重要
2. 知识在 Harness Engineering 中到底处于什么位置
3. 我们如何设计知识分层架构，让知识真正可以沉淀、共享和升级
4. 工作流如何反过来成为知识沉淀的载体
5. 为什么人机交互方式本身，也会影响知识闭环能否真正跑通

---

## 一、从 Harness Engineering 热潮说起 / Starting From The Harness Engineering Wave

2025 年末到 2026 年初，AI 工程领域出现了一波关于 Harness Engineering 的集中讨论。

这个术语的隐喻并不复杂：

就像骑师不是去增强马本身的体能，而是通过缰绳、鞍具和约束系统，让马的力量走向正确的方向；Harness Engineering 强调的也不是一味增强模型，而是设计一层工程化控制系统，让模型的能力被稳定、可控地释放出来。

从业界几种有代表性的实践来看，不同团队的关注点并不一样：

| 实践方 | 核心关注 | 关键动作 |
|---|---|---|
| OpenAI — Codex | 人机交互协议 | 通过精确指令协议与运行环境约束 Agent |
| Cursor — Self-Driving | 多 Agent 协同 | 背景 Agent 自动检测冲突并运行测试 |
| Anthropic — Claude Code | 长时运行稳定性 | 用长期记忆、规则文件和控制面降低复杂任务漂移 |

这些实践都很有启发性。  
但在我们团队自己的深度实践中，一个更本质的问题逐渐浮了出来：

**工作流只是管道，知识才是流过管道的活水。**

工作流当然重要。  
但如果每次需求都从零开始，每次都重新踩一遍上次已经踩过的坑，每次都重新推导一遍之前已经验证过的架构决策，那么再复杂的 Agent 编排，本质上也只是一个高成本的一次性系统。

这就是我们越来越坚定的判断：

> 将来的技术护城河不在模型，也不只在工作流，而在垂直领域知识的沉淀。

Skill 会随着模型迭代。  
Agent 形态会随着工具链演进。  
Workflow 编排方式也会不断变化。  
但领域知识是长期资产。

这也是我们在 AI Team 项目中持续坚持的一条理念：

**Skill、Agent、工具链会随模型迭代更新，但领域知识是永恒的。**

## 二、Harness Engineering 的三支柱，以及知识到底在哪里 / The Three Pillars Of Harness Engineering And Where Knowledge Sits

在我们看来，Harness Engineering 的核心可以概括成三个支柱：

- 上下文工程
- 架构约束
- 持续治理

把它展开，大致会变成这样：

| 支柱 | 关注点 | 典型能力 |
|---|---|---|
| 上下文工程 / Context Engineering | 给模型什么信息、什么时候给、给多少 | 长短期记忆、知识检索、渐进式披露、上下文防火墙 |
| 架构约束 / Architecture | 系统如何编排、如何降级、如何保持边界 | Agent 编排模式、状态机设计、执行安全边界、降级策略 |
| 持续治理 / Governance | 系统如何长期保持健康，而不是越跑越乱 | 质量门禁、知识生命周期、自动衰减、持续进化 |

如果你仔细看，会发现知识不是附属品，而是直接嵌在这三层结构里的：

- 在上下文工程里，知识决定模型到底能读到什么
- 在架构约束里，知识影响工作流怎样做判断和选择
- 在持续治理里，知识本身也有生命周期、成熟度和淘汰机制

换句话说：

**知识管理本身就是 Harness Engineering 的核心能力，而不是边缘功能。**

只是当前很多讨论更喜欢聚焦那些更显眼的话题，比如：

- 工作流怎么编排
- 多 Agent 怎么协同
- 上下文怎么裁剪
- 运行时怎么接更多工具

这些当然都重要。  
但如果底层没有一个会沉淀、会升级、会治理的知识基础设施，整个 Harness 最后还是会变成一套高成本但低复用的操作流。

## 三、为什么知识沉淀比工作流本身更重要 / Why Knowledge Matters More Than The Workflow Itself

我们在实践里越来越明确地形成了三个判断。

### 3.1 工作流是可替换的，知识是可累积的 / Workflows Are Replaceable, Knowledge Is Accumulative

今天你可能用 16 阶段状态机。  
明天可能换成 DAG。  
后天可能换成更轻量的事件驱动协作模式。

Agent 的编排方式会变。  
Runtime 会变。  
工具协议会变。  
模型也会变。

但一条经过实践验证的知识不会因为这些变化而失效。

比如：

“广告预算扣减在高并发下会超扣，必须用 Redis + Lua 保证原子性。”

这条知识不依赖某个模型，不依赖某条 workflow，不依赖某个 Agent 编排图。  
它是一条真正可复用、可迁移、可复利的工程知识。

### 3.2 没有知识沉淀的工作流，本质上是一次性的 / A Workflow Without Knowledge Retention Is Disposable

我们观察到一个很典型的反模式：

团队搭了很复杂的 Agent 工作流，每次需求都跑一遍完整流程，但每次都像第一次一样从零开始。

表现出来就是：

- 上一次踩过的坑，下一次继续踩
- 上一次做过的架构取舍，下一次重新推导
- 上一次验证过的路径，下一次还要重新试错

这类系统不是没有工作流，而是没有知识闭环。

换句话说，团队投入了很多工程成本去搭工具链，却没有让工具链变得越来越聪明。

### 3.3 知识是团队的复利资产 / Knowledge Is The Team’s Compounding Asset

我们把团队知识粗略分成三类：

- 散点型知识：孤立事实
- 因果型知识：为什么 A 导致 B
- 时空型知识：某个场景、某个阶段下才成立的经验

越是高阶的知识，越难通过通用模型直接获得，越依赖团队自己的实践沉淀。

当你的知识库中积累了成百上千条经过验证的知识条目时：

- 新成员会站在前人肩上
- 新项目会自动受益于旧项目积累
- 新工作流不再是从零开始

这就是知识的复利效应。

## 四、我们的知识分层架构：不是堆文档，而是做知识系统 / Our Layered Knowledge Architecture

在 AI Team 系统中，我们不是简单做一个“文档库”，而是设计了一套三维正交的知识架构。

这三个维度分别回答三个问题：

| 维度 | 回答的问题 | 定义 |
|---|---|---|
| 存储层 | 知识存在哪里 | 从个人、本团队、通用技术、通用业务到项目局部 |
| 知识类型 | 知识描述的是什么 | model / decision / guideline / pitfall / process |
| 成熟度 | 这条知识多可信 | draft → verified → proven |

### 4.1 五层存储架构 / Five Storage Layers

我们把知识的存储边界设计成五层：

| 层级 | 含义 | 共享范围 |
|---|---|---|
| Layer 0-P | 个人偏好 | 纯本地，不共享 |
| Layer 0-T | 团队约定 | 团队级共享 |
| Layer 1 | 技术知识 | 团队级，跨项目复用 |
| Layer 2 | 业务知识 | 团队级，按业务域复用 |
| Layer 3 | 项目知识 | 项目级，跟随项目 |

为什么要分层？

因为不同范围的知识，本来就应该有不同的生命周期和共享边界。

- “我喜欢 2 空格还是 4 空格”是个人偏好
- “团队统一的 commit 规范”是团队约定
- “Spring Boot 多租户拦截器模式”是跨项目技术知识
- “广告审核流程：提交→机审→人审→上线”是业务域知识
- “这个项目接的是 TencentDB for MySQL 8.0”是项目局部知识

更重要的是，知识不是固定不动的。

Layer 3 的项目知识，如果被验证为跨项目通用，就应该向上提升到 Layer 1 或 Layer 2。

也就是说，知识架构本身要支持“提升”，而不是只支持“存放”。

### 4.2 五种知识类型 / Five Knowledge Types

知识按“它到底描述的是什么”分类，我们在实践里把它收敛成五类：

| 类型 | 定义 | 示例 |
|---|---|---|
| model | 实体、字段、关系、结构定义 | “广告计划包含预算、出价、投放时段三个核心字段” |
| decision | 技术选型、架构决策及其理由 | “选择事件驱动而非同步 RPC，因为状态变更需要解耦” |
| guideline | 推荐做法或禁止做法 | “公共模块变更后的兼容性检查清单” |
| pitfall | 已知风险、故障模式、排查步骤 | “广告预算扣减在高并发下会超扣” |
| process | 业务流程、状态机、操作步骤 | “广告审核：提交→机审→人审→上线” |

这五类最大的价值，不是分类本身，而是让 Agent 和人都知道：

- 当前查到的到底是什么类型的知识
- 它应该在什么场景下被引用
- 它是“事实”、“判断”、“建议”、“风险”还是“流程”

### 4.3 三级成熟度与自动衰减 / Three Maturity Levels And Automatic Decay

知识不能只进不出，也不能写完就永久有效。

所以我们给知识设计了成熟度：

- `draft`：新提取，单一来源，初步可信
- `verified`：已经在一个项目或一个工作流里被验证过
- `proven`：在多个项目或多个工作流中反复成立

更重要的是，我们认为成熟度不应该只升不降。

知识如果长期不被引用，或者环境已经发生变化，就应该自动衰减：

- `proven` 长期不用，降回 `verified`
- `verified` 长期不用，降回 `draft`
- 长期无人引用且被 Lint 标记的问题条目，归档退出活跃索引

为什么一定要有衰减？

因为知识也会过时。  
一条三年前的“最佳实践”，很可能在框架升级后已经不再最佳。

如果知识不会退出，它迟早会反过来误导 Agent。

## 五、团队知识库：为什么必须独立出来 / Why The Team Knowledge Base Must Be Separate

我们做了一个关键决策：团队知识库必须是独立 Git 仓库，而不是寄生在某个业务项目里。

原因很简单。

### 5.1 知识需要跨项目共享 / Knowledge Must Be Shared Across Projects

如果知识只属于单个项目，那么项目 A 踩过的坑，项目 B 不会自动继承。

而独立知识仓库意味着：

- 多个项目连到同一知识源
- 项目 A 沉淀的经验，项目 B 自动受益
- 团队的认知不会随着项目结束而消失

### 5.2 知识的生命周期不应依附于业务仓库 / Knowledge Should Not Die With The Repo

业务项目会归档、会重构、会迁移。  
知识不应该跟着仓库生命周期一起消失。

把知识独立出来，本质上是在承认一件事：

**知识是一级资产，不是代码仓库的附属品。**

### 5.3 知识管理需要独立权限与角色 / Knowledge Needs Its Own Roles And Governance

在我们的设计里，知识库不是“所有人随便写”的共享文件夹，而是带角色和共识机制的系统。

大致可以分成：

- `maintainer`：负责裁决冲突、审批提升、维护规则
- `contributor`：可以通过工作流自动贡献知识
- `reader`：可以消费知识，但不能直接改动

这不是为了增加流程，而是为了确保：

- 知识可以低摩擦共建
- 关键冲突有人裁决
- 成熟度提升是基于共识，而不是单点自说自话

## 六、工作流的真正作用：不是跑流程，而是沉淀知识 / The Real Job Of The Workflow Is Knowledge Retention

回到工作流本身。

在 AI Team 系统中，16 阶段状态机不是为了显得复杂，而是为了让知识在每次执行中都能流动起来。

一个完整的知识生命周期，大致是这样：

### INIT：注入知识 / Inject Knowledge

工作流启动时，先拉团队知识仓库，把知识目录和查询入口注入 Agent。

这意味着新工作流不是从零开始，而是从已有知识出发。

### 执行中：消费知识 / Consume Knowledge

不同阶段的 Agent 在不同决策点，按需查询不同类型的知识。

比如：

- 产品分析阶段，更多查业务模型和流程知识
- 技术分析阶段，更多查技术决策和反模式
- 实现阶段，更多查 guideline 和 pitfall

这一步的关键不是“给 Agent 更多知识”，而是“让 Agent 在正确的阶段看正确的知识”。

### ARCHIVE：提取知识 / Extract Knowledge

工作流结束后，系统会从产物中自动提取知识条目：

- 架构决策变成 `decision`
- 已知风险变成 `pitfall`
- 复用经验变成 `guideline`
- 新流程变成 `process`

然后再根据通用性判定：

- 留在项目层
- 提升到技术层
- 提升到业务层

这意味着每次交付都不仅是在“完成一个需求”，也是在“给团队知识库再加一层地基”。

## 七、知识怎么被精准消费：不是推送，而是按需查询 / Knowledge Should Be Queried, Not Dumped

传统做法常常是在 Agent 启动时，把一堆知识直接推给它。

这会有两个问题：

- 信息过载
- 不精准

我们更倾向于一种按需查询的模式。

### 7.1 三级渐进式索引 / Three-Level Progressive Index

知识库本身不应该是一坨平铺文档，而应该至少有三层：

| 层级 | 作用 |
|---|---|
| 全景目录 | 知道知识库里大概有什么 |
| 分类清单 | 知道这个类别下有哪些条目 |
| 完整条目 | 只有需要时才深入读 |

这意味着 Agent 不需要一上来就吞下全部知识，而是：

1. 先看知识库地图
2. 再缩小到相关分类
3. 最后只读真正需要的知识条目

### 7.2 查询预算 / Query Budget

查询也应该有预算。

因为上下文膨胀本身就是 Harness Engineering 要解决的问题之一。

如果知识库查阅没有成本控制，系统最后会重新回到：

- 读太多
- 带太多
- 反而更不准

所以我们更倾向于：

**让知识消费变得精准，而不是贪婪。**

### 7.3 引用追踪闭环 / Reference Tracking Loop

知识被使用，不应该只是“读过了”，而应该留下引用记录。

这样才能形成闭环：

- 被高频引用的知识，成熟度上升
- 长期不引用的知识，成熟度下降
- 系统真正知道哪些知识在持续产生价值

这也是知识库能长期保持“活”的关键。

## 八、为什么人机交互方式也会影响知识闭环 / Why Human Interaction Design Affects The Knowledge Loop

这可能是很多团队最容易忽略的一点。

工作流设计得再好，如果它在关键节点必须等人，而人又不在场，整个闭环就会被卡住。

这不是知识问题，但会直接影响知识沉淀的节奏。

### 8.1 真正的问题：工作流依赖人的在场 / The Real Bottleneck Is Human Availability

很多 Agent 工作流都隐含一个假设：

操作者坐在电脑前，IDE 开着，随时可以响应。

现实并不是这样。

人在开会、通勤、吃饭、跨团队沟通的时候，工作流里的确认节点就会停住。

结果就是：

- 交付周期被拉长
- 知识沉淀被延后
- 碎片时间被浪费

### 8.2 我们的解法：远程接管与异步审批 / Our Practical Answer: Remote Handoff And Async Approval

在实际工程中，我们引入了远程操控能力，让人可以在手机、平板、浏览器上接管正在开发机上运行的会话。

这带来的价值，不只是“操作更方便”，而是：

- 工作流不再只依赖工位前的时间
- 关键确认节点可以在碎片时间完成
- 工作流可以更连续地走完
- 知识注入、消费、提取的完整闭环更容易跑通

### 8.3 这背后的架构启示 / The Architectural Lesson Behind It

这件事给了我们一个很重要的启示：

**好的 Harness 不只要设计 Agent 怎么跑，还要设计人怎么随时参与。**

这意味着：

- 状态要持久化
- 断点要可恢复
- 审批要异步
- 关键节点要能主动通知

这些设计看起来像“交互问题”，但本质上是在保障知识闭环不中断。

## 九、落地经验：从文件即状态到知识即资产 / From File-As-State To Knowledge-As-Asset

AI Team 的一个核心设计哲学是：

**文件系统即状态机。**

也就是说：

- 状态存在文件里
- 产物存在文件里
- 知识存在文件里

我们没有把知识做成一个完全黑盒的平台，而是保留它的可见性、可编辑性和可版本化。

这么做的好处很直接：

- 人可以直接阅读知识
- Git 天然提供版本历史
- 知识不会依附某个平台而失去迁移能力
- 换模型、换工具链时，沉淀下来的知识不会消失

从这个角度看，真正被长期保存下来的，不是某条工作流，而是工作流持续沉淀出的知识资产。

## 十、总结：Harness 是手段，知识才是目的 / Conclusion: Harness Is The Means, Knowledge Is The End

回到文章开头的核心判断：

**Harness 不是目的，知识才是护城河。**

我们在 AI Team 项目中的实践，最终收敛出几个判断：

- 知识需要被分层管理，而不是散落在项目里
- 团队知识库需要共建共享，而不是停留在个人经验
- 工作流的真正价值之一，是让每次交付都能转化成知识沉淀
- 知识消费必须精准，而不是无上限灌输
- 知识要有生命周期，而不是永远堆积
- 人机交互模式也会影响知识闭环的完整性

展望未来，我们认为有几个方向特别值得继续探索：

- 更强的语义检索与知识发现
- 跨团队的知识联邦共享
- 基于真实使用效果的知识质量评估
- 更彻底的异步人机协作工作流

但无论工具如何变化，有一件事不会变：

模型会升级，Agent 会重构，Workflow 会替换。  
真正值得长期积累的，是团队在垂直领域里的知识。

所以如果要用一句话概括我们的结论，那就是：

**工作流是手段，知识是目的；Harness 是通路，知识才是护城河。**
